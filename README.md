# Transaction Ledger API

A backend API for the Full Stack Developer Assessment. It supports account creation, credit/debit transactions, balance lookup, filtered and paginated transaction history, and atomic money transfers.

## Technology

- Node.js 20+
- Express.js
- PostgreSQL
- Zod request validation
- `pg` for database access

## Prerequisites

Install Node.js 20 or newer and PostgreSQL. Create a database named `transaction_ledger`.

Example using `psql`:

```sql
CREATE DATABASE transaction_ledger;
```

## Setup

1. Open this folder in VS Code.
2. Install packages:

   ```bash
   npm install
   ```

3. Copy `.env.example` to `.env`.
4. Update `DATABASE_URL` in `.env` with your PostgreSQL username and password.
5. Create the tables and indexes:

   ```bash
   npm run db:init
   ```

6. Start the API:

   ```bash
   npm run dev
   ```

The API runs at `http://localhost:4000`. Health check: `GET http://localhost:4000/health`.

## API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/accounts` | Create an account; balance is always initialized to 0 |
| GET | `/api/accounts/:accountId/balance` | Get the current balance |
| POST | `/api/accounts/:accountId/transactions` | Create a credit or debit transaction |
| GET | `/api/accounts/:accountId/transactions` | Get transaction history with optional filtering and pagination |
| POST | `/api/transfers` | Bonus: transfer money atomically between accounts |

See [`API_DOCUMENTATION.md`](./API_DOCUMENTATION.md) for request/response examples and status codes.

## Important implementation details

- Account IDs and transaction IDs are generated by the server as UUIDs.
- Client-supplied account balances and unknown fields are rejected.
- PostgreSQL constraints enforce valid transaction types, positive amounts, account references, non-negative balances, and unique `(account_id, reference_id)` pairs.
- Account rows are locked with `SELECT ... FOR UPDATE` before changing balances, so simultaneous transactions against the same account are serialized.
- Creating a transaction and changing the balance happen inside one database transaction. Failures trigger a rollback.
- A duplicate reference ID for the same account returns HTTP `409` and does not change the balance.
- A debit that exceeds the balance returns HTTP `422`.
- Transaction history is ordered newest first and supports `type`, `page`, and `limit`.
- There are intentionally no transaction update or delete endpoints. Ledger entries are immutable through this API.
- Money transfer locks both account rows in a consistent order and writes both ledger entries and balance changes in one database transaction.

## Example requests

Create an account:

```bash
curl -X POST http://localhost:4000/api/accounts \
  -H "Content-Type: application/json" \
  -d '{"name":"Likhitha"}'
```

Credit an account (replace `ACCOUNT_UUID`):

```bash
curl -X POST http://localhost:4000/api/accounts/ACCOUNT_UUID/transactions \
  -H "Content-Type: application/json" \
  -d '{"type":"credit","amount":100,"description":"Initial deposit","reference_id":"deposit-001"}'
```

Check the balance:

```bash
curl http://localhost:4000/api/accounts/ACCOUNT_UUID/balance
```

List transactions:

```bash
curl "http://localhost:4000/api/accounts/ACCOUNT_UUID/transactions?type=credit&page=1&limit=10"
```

## Error response format

```json
{
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "The account does not have sufficient balance."
  }
}
```

Validation errors include a `details` array identifying invalid fields.

## Assumptions

1. All monetary values are expressed in one currency; the API does not perform currency conversion.
2. Amounts are submitted as JSON numbers and stored as PostgreSQL `NUMERIC(14,2)`.
3. `reference_id` is unique per account, not globally.
4. Account and transaction identifiers are UUIDs generated by the server.
5. Transactions are immutable through this API; no edit/delete endpoints are exposed.
6. The transfer endpoint is included as a bonus feature. It writes a debit and credit transaction with derived reference IDs, while the client-supplied transfer reference is returned in the response.
7. Authentication and authorization are not specified in the assessment and are not implemented in this version.
